# 个人笔记复习助手：项目取舍与面试准备

## v1.1 取舍：为什么引入单 Agent

原先用关键词规则跳过检索，速度快，但规则覆盖有限，例如“你好你是谁”这类口语组合容易漏掉；快速模式改为让模型通过工具调用自主决策，精确查找保留固定 RAG 链路。

- 收益：快速模式的基础问答不访问知识库；知识问题由 Agent 明确调用检索工具；精确查找仍可作为完整固定链路对照。
- 代价：快速模式中需要检索的问题多一次 Agent 决策模型调用，首字速度可能变慢。
- 当前边界：只实现单 Agent、单检索工具，不做无限循环、多 Agent 协作或联网搜索，便于实习项目讲清楚和验证。
- 缓存现状：模型与 Cross-Encoder 已有进程内初始化缓存；尚未做“问题到答案”的结果缓存，后续要基于耗时数据决定是否加入。

## 1. 项目定位

**面向谁**：需要复习课程、技术笔记的学生。

**解决什么问题**：笔记分散，复习时难以定位原文；普通聊天模型也无法保证答案来自自己的学习资料。

**为什么用 RAG**：把本地笔记作为可更新、可追溯的外部知识；回答前先找依据，再生成带来源的说明。它不是为了“消灭一切幻觉”，而是降低无依据回答，并让用户回看原文。

## 2. 技术点不是堆砌，而是逐个解决问题

| 发现的问题 | 方案 | 代价 / 边界 |
| --- | --- | --- |
| 用户问题口语化、带“刚才那个”等指代 | 查询改写为完整检索问题 | 多一次模型调用；改写失败时回退原问题 |
| 纯向量检索可能漏掉术语、函数名、缩写 | BM25 补充关键词召回 | 要维护中文分词和额外索引 |
| 两路检索分数尺度不同，不能直接相加 | RRF 按排名融合 | 不使用原始分数，需选择 k 参数 |
| 相关资料进入候选池但排不到前面 | Cross-Encoder 精排候选片段 | 增加推理延迟；只能重排已召回内容 |
| 模型可能脱离笔记回答 | Prompt 限制、来源引用、资料不足拒答 | 不能回答知识库之外的问题 |
| 问答和小测属于不同任务 | 后续用单 Agent 在两个工具间路由 | 不是 v1 必需功能，不能替代检索优化 |

## 3. 项目范围与实现顺序

### 必须完成（MVP）

1. 本地 Markdown 笔记导入、标题切分、来源元数据保存。
2. 查询改写 → 向量检索 + BM25 → RRF → Cross-Encoder 精排。
3. 基于最终片段的带来源问答；无依据时明确拒答。
4. Streamlit 页面：笔记导入、提问、答案、来源片段。

### 有时间再做

1. 基于当前笔记章节生成 3 道小测。
2. 单 Agent 在“问答”和“小测”工具之间路由。

### 不做

- RAGAS、自动化评测平台、复杂多轮自检。
- 多 Agent、LangGraph、联网搜索、登录与云端部署。

## 4. 最小验证证据（不做完整评测模块）

准备 10 个自己已知答案的问题，其中覆盖概念解释、术语、跨章节问题和笔记外问题。

| 对比项 | 记录方式 | 目的 |
| --- | --- | --- |
| 仅向量检索 | 记录正确来源是否进入 Top-3 | 形成基线 |
| 混合检索 + 精排 | 用同一题记录 Top-3 来源 | 判断优化是否帮助召回和排序 |
| 笔记外问题 | 记录是否正确拒答 | 验证回答边界 |

这份表只作为 README 和面试的离线验证证据。没有真实线上流量时，不能声称生产级效果，也不能编造“准确率提升”。

## 5. 面试回答通用顺序

每题按以下顺序回答：

`结论 → 项目事实 / 症状 → 方案与取舍 → 自己的验证 → 适用边界`

例如，不说“Rerank 提升明显”，而说：先说明候选片段已召回但排序靠后；因此对候选做精排；它增加延迟且无法找回没召回的资料；最后用自己的 10 题验证表说明结果。

## 6. 可能追问与回答要点

### 1）为什么要用 RAG？

因为用户要问的是自己的课程/技术笔记，资料会增加且需要回看出处。模型参数中没有这些私有笔记；RAG 能在回答前检索证据并展示来源。固定格式或纯闲聊不需要强行上 RAG。

### 2）完整链路是什么？

离线侧：导入笔记、清洗、按 Markdown 标题切分、补充文件名和章节元数据、建立向量与 BM25 索引。在线侧：改写查询、双路召回、RRF 融合、Cross-Encoder 精排、带来源生成；无依据时拒答。

### 3）为什么先做查询改写？

真实提问常含“刚才那个”“它有什么区别”这类指代。改写把它补全成独立检索问题，使关键词和语义检索更稳定。改写不是无条件相信：失败或空结果时会保留原问题继续检索。

### 4）为什么不能只用向量检索？

向量检索擅长语义相近，但课程术语、函数名和缩写往往需要精确关键词命中。BM25 补召回；两路各有优劣，因此再用 RRF 合并候选。

### 5）为什么用 RRF，而不直接合并分数？

向量相似度和 BM25 分数不在同一尺度，直接相加没有可靠含义。RRF 只依据每路排名，计算简单、对分数尺度不敏感；代价是丢失了原始分数的绝对差异。

### 6）为什么还要 Rerank？

混合检索解决“相关资料有没有进候选池”，精排解决“候选里真正有用的片段是否排在前面”。精排更慢，所以只处理 RRF 后的少量候选；如果资料根本没召回，Rerank 无法补救。

### 7）答案不准时怎样排查？

先查看 Top-K 是否包含支持正确答案的片段：没有则排查资料、切分、查询改写、Embedding 和召回；有但排序靠后则检查 RRF、Top-K 与 Rerank；有且排序合理但回答错误，则检查 Prompt、上下文冲突或模型生成。一次只改一个变量。

### 8）如何证明优化有效？

项目没有线上流量，因此只做离线小样本验证：用固定的 10 个问题，对比纯向量与混合检索+精排的 Top-3 来源命中，并保留失败例子。只报告实际记录的数据，不把它包装成生产准确率。

### 9）为什么需要 Agent？

v1 的核心不是 Agent，而是检索质量。后续如果有“笔记问答”和“章节小测”两项工具，再让单 Agent 根据用户意图选择工具。不会为了演示 Agent 让所有问题都先走一轮无意义判断。

### 10）Chunk、Top-K 等参数如何确定？

先按 Markdown 标题保护章节语义；Chunk 不能过小导致上下文断裂，也不能过大混入多个主题。Top-K、RRF 参数和精排候选数先取小范围候选，再用固定问题观察来源命中、答案噪声和响应速度；不把某个数字说成行业标准。

### 11）向量检索、BM25、RRF、Cross-Encoder 分别做什么？

向量检索返回语义相近的 Chunk，擅长口语化、同义表达；BM25 按关键词匹配，擅长函数名、缩写、模型名和错误码等精确术语。RRF 融合两路召回结果，只按每路排名计算融合分，让两路都靠前的 Chunk 排得更高。Cross-Encoder 将“问题 + 候选 Chunk”一起输入模型，重新计算更精确的相关性分数，做最终精排。

### 12）RRF 的具体流程是什么？

查询改写后，向量检索和 BM25 分别返回各自的 Top-K。RRF 以 `chunk_id` 判断两个结果是否是同一个 Chunk，并按 `1 / (k + rank)` 累加每一路的排名分，最后按总分排序。它不接收用户问题，也不重新检索，只融合两路已经得到的结果。

### 13）为什么 RRF 不直接相加向量分数和 BM25 分数？

Chroma 的距离分数和 BM25 的关键词相关分数含义、范围都不同，直接相加没有可靠的比较基础。RRF 放弃原始分数，只看“在该路排第几名”，因此可以安全融合两种不同的检索方式。

### 14）为什么需要 Cross-Encoder？

向量检索、BM25 和 RRF 的目标是快速召回候选片段，但候选中仍可能有“关键词像、实际却不能回答问题”的内容。Cross-Encoder 将问题和每个候选片段一起输入 Transformer，做更细粒度的相关性判断，把真正能回答的问题排到前面。代价是每个“问题-片段”组合都要推理，因此只精排 RRF 后的少量候选；它也无法找回根本没有召回的资料。

**面试简版**：前面的向量检索和 BM25 是先把可能相关的资料找出来，但排在前面的不一定最能回答问题。Cross-Encoder 会把问题和候选片段放在一起重新判断相关性，把最合适的片段排到前面。因为它比较慢，所以只处理前面召回的一小部分结果。

**追问：为什么会比较慢？** 因为它需要把“问题 + 每一个候选片段”分别送进模型算一次分数。比如有 10 个候选片段，就要进行 10 次推理；候选越多，耗时越长，因此不能对整个知识库的所有 Chunk 都使用它。

## 7. 面试时必须守住的边界

- 这是本地离线 Demo，不宣称高并发、线上规模、生产监控或大规模评测。
- 代码可以在 Codex 协助下完成，但只能说自己能运行、理解、修改并解释的部分。
- RAGAS 在学习中验证过，但本项目不使用；不要把课程练习结果写成项目指标。
- 所有“改进效果”必须来自项目实际的固定问题记录。
# 新增取舍：为什么提供快速模式与精确查找？

**结论：** 不是每个问题都值得走混合检索和 Cross-Encoder，因此把速度与检索质量做成用户可选择的两条链路。

**项目事实：** 普通概念复习只需要语义相近片段时，查询改写、BM25、RRF 与精排会增加等待时间；函数名、缩写、专有术语等问题又确实需要更完整的召回与排序。

**取舍：** 快速模式只走向量检索，速度和成本更低，但可能漏掉精确关键词；精确查找走改写、双路召回、RRF 和 Cross-Encoder，候选更全面但延迟更高。

**面试回答：** “我没有把完整 RAG 链路当成所有场景的默认答案。项目中把纯向量检索保留为快速模式，把混合检索和精排提供为精确查找。用户根据问题类型选择；后续用固定问题集分别记录来源命中和端到端耗时，再决定默认模式是否需要调整。”

## 新增说明：当前如何验证 RAG 效果

当前项目没有专门建立 RAG 评估集，所以没有准确率、Recall 等量化数据，也不会在面试中编造这些数字。

目前主要用真实问题做人工验证：

1. 精确查找先通过向量检索和 BM25 找候选片段，再用 RRF 与 Cross-Encoder 排序；最后把用户问题和排在前面的片段交给大模型判断是否足够回答。
2. 正例：笔记里有 Git 常用命令时，问 Git 命令应该能基于笔记回答出来。
3. 反例：笔记只有 Docker 部署 MySQL 的内容时，问 MySQL 基础概念应该明确提示资料不足，而不是把局部资料包装成完整答案。
4. 后续会把这些成功和失败问题整理成固定测试题，再比较不同参数或方案调整前后的结果。

**面试简答：** “我现在还没有完整的 RAG 评估集，所以没有准确率、Recall 这些量化数据。当前先通过真实问题验证：该答出来的是否能基于笔记答出；资料只覆盖局部时，是否能如实提示资料不足。后续会把这些案例整理成固定测试题，再做改动前后的对比。”
