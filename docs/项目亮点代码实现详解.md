# Personal Notes Review Assistant 项目亮点代码实现详解

> 用途：换电脑后快速恢复项目上下文，也可用于面试复习。本文以当前仓库代码为准。

## 一、项目核心流程

```text
文件上传
  ↓
Markdown / ZIP / 单独图片解析
  ↓
图片提取与视觉模型描述
  ↓
增强 Markdown + 独立图片块
  ↓
标题切分并写入 Chroma
  ↓
统一混合检索
  ↓
大模型流式回答
  ↓
前端展示答案、来源和命中图片
```

当前默认前端是 `streamlit_demo.py`，直接调用后端 service；`frontend/app.py` 是保留的 FastAPI 分离部署版前端。

## 二、文件上传与图文 Markdown

### 1. 上传入口

入口文件：`backend/app/api/notes.py`

核心函数：

```python
@router.post("/import")
async def import_note(
    file: UploadFile = File(...),
    api_key: str = Depends(require_user_deepseek_api_key),
) -> ImportResult:
```

支持：

- `.md`
- `.zip`，用于同时上传 Markdown 和本地图片
- `.jpg/.jpeg/.png/.webp`

普通 `.md` 中如果引用本地相对路径图片，后端无法单独取得图片，应将 Markdown 和图片一起打包为 ZIP。

### 2. 图片引用提取

文件：`backend/app/services/markdown_image_service.py`

```python
MARKDOWN_IMAGE_PATTERN = re.compile(
    r"!\[(?P<alt>[^\]]*)\]\((?P<source>[^\s)]+)(?:\s+[^)]*)?\)"
)

matches = list(MARKDOWN_IMAGE_PATTERN.finditer(markdown))
```

每个 `match` 包含图片地址及其在 Markdown 中的位置，后续可以准确回填描述。

支持三类来源：

```python
if source.lower().startswith("data:image/"):
    image_bytes, mime = _decode_data_uri(source)
elif source.lower().startswith("https://"):
    image_bytes, mime = await _download_remote_image(source)
elif local_images:
    image_bytes, mime = local_images[normalized_source]
```

- Base64 Data URI
- 公网 HTTPS 图片
- ZIP 中的本地图片

远程图片会检查协议和 IP，阻止访问本机或内网地址，降低 SSRF 风险。

### 3. 调用视觉模型

图片先保存到本地，再转成 Base64 Data URL：

```python
local_path = await asyncio.to_thread(
    save_image_to_local,
    image_bytes,
    mime,
    doc_dir,
)

description = await describe_image_url(
    image_path_to_data_url(local_path),
    api_key,
)
```

视觉模型实际接收：

```text
data:image/png;base64,...
```

并返回图片的文字描述。

### 4. 增强 Markdown

```python
replacement = f"{match.group(0)}\n\n> 图片内容：{description}"
```

处理前：

```markdown
![JVM结构图](images/jvm.png)
```

处理后：

```markdown
![JVM结构图](images/jvm.png)

> 图片内容：该图片展示了 JVM 运行时数据区……
```

替换从后往前执行，避免前面插入文字后影响后面图片的位置下标。

### 5. 独立图片块

每张成功处理的图片还会生成独立 `Document`：

```python
metadata = {
    "source": source_path,
    "image_path": local_path,
    "is_image_chunk": True,
    "doc_id": doc_id,
}

metadata.update(_headers_before(markdown, match.start()))

image_chunk = Document(
    page_content=description,
    metadata=metadata,
)
```

向量化的是视觉模型生成的 `description`，不是原图或 Base64。

图片块 metadata 包括：

- `chunk_id`
- `source`
- `doc_id`
- `image_path`
- `is_image_chunk`
- `Header 1/2/3`

### 6. Markdown 切分

文件：`backend/app/services/note_splitter.py`

```python
headers_to_split_on = [
    ("#", "Header 1"),
    ("##", "Header 2"),
    ("###", "Header 3"),
]

markdown_splitter = MarkdownHeaderTextSplitter(headers_to_split_on)
chunks = markdown_splitter.split_text(doc.page_content)
```

当前真实逻辑是：

- 所有 Markdown 都统一按照 H1/H2/H3 切分。
- 图文 Markdown 会先回填图片描述，再按标题切分。
- 图片描述还会额外生成独立图片块。
- 当前没有对过长标题块进行字符数或 Token 二次切分。

最后：

```python
chunks.extend(image_result.image_chunks)
knowledge_to_vector(chunks)
```

普通标题块和图片块统一写入 Chroma。

## 三、统一混合检索

入口文件：`backend/app/services/rag_service.py`

整体流程：

```text
加载全部文本块和图片块
  ↓
必要时查询改写
  ↓
向量 Top-6 + BM25 Top-6
  ↓
相关性门槛判断
  ↓
RRF 排名融合
  ↓
BGE Cross-Encoder 精排
  ↓
取 Top-3 交给大模型
```

### 1. 加载语料

```python
@lru_cache
def load_all_chunks() -> tuple[Document, ...]:
    for file_path in UPLOAD_DIRECTORY.glob("*.md"):
        all_chunks.extend(split_documents(load_notes(str(file_path))))
        all_chunks.extend(load_image_chunks(file_path))

    all_chunks.extend(load_standalone_image_chunks(UPLOAD_DIRECTORY))
    return tuple(all_chunks)
```

导入新笔记后清空缓存，并要求下一次查询重建 BM25：

```python
load_all_chunks.cache_clear()
_bm25_rebuild_required = True
```

### 2. 查询改写

```python
rewritten_query = query_rewrite(original_query, chat_model)
```

只有问题包含“刚才、前面、它、那个”等指代时才调用模型改写。完整问题通常直接保留。

改写结果只用于检索，最终回答仍使用用户的原始问题。

### 3. 双路召回

```python
vector_results = vector_retriever(
    query=rewritten_query,
    vector_store=vector_store,
    top_k=6,
)

bm25_results = bm25_retriever(
    query=rewritten_query,
    chunks_list=all_chunks,
    top_k=6,
)
```

- 向量检索负责语义相似。
- BM25 配合 `pkuseg` 中文分词，负责关键词、类名、命令等精确匹配。

### 4. 相关性门槛

```python
has_relevant_material = (
    best_vector_distance is not None
    and best_vector_distance <= 1.10
) or has_keyword_hit
```

满足任意条件才继续：

- 最佳向量距离不大于 `1.10`。
- BM25 至少存在一个大于 0 的分数。

否则直接返回资料不足，减少无依据回答。

### 5. RRF 融合

```python
rrf_results = rrf_fusion([vector_results, bm25_results])
```

RRF 不直接混合两种不同量纲的分数，而是按照排名计算：

```text
1 / (60 + rank)
```

同一 `chunk_id` 如果同时被两路召回，分数会累计。

### 6. Cross-Encoder 精排

```python
reranked_results = cross_encoder_reranker_index(
    query=rewritten_query,
    rrf_results=rrf_results,
    cross_encoder=get_reranker_model(),
    top_k=3,
)
```

模型：`BAAI/bge-reranker-base`。

它直接对“问题—候选内容”进行相关性打分，最终保留 Top-3。如果本地缺少精排依赖，系统会降级为 RRF Top-3。

## 四、历史 Agent 与记忆实现

> 本节记录项目早期快速模式的实现，当前统一问答链路已不再调用 `agent_service.py`，也不使用多轮会话记忆。保留代码是为了复盘从 Agent 分流到固定 Workflow 的演进。

文件：`backend/app/services/agent_service.py`

预定义中间件叫：

```python
SummarizationMiddleware
```

完整配置：

```python
return create_agent(
    model=chat_model,
    tools=[search_personal_notes],
    system_prompt=FAST_AGENT_SYSTEM_PROMPT,
    middleware=[
        DeepSeekToolCallMiddleware(),
        SummarizationMiddleware(
            model=chat_model,
            trigger=("messages", 14),
            keep=("messages", 12),
            trim_tokens_to_summarize=1200,
            summary_prompt=MEMORY_SUMMARY_PROMPT,
        ),
    ],
    checkpointer=checkpointer,
)
```

职责划分：

- `SummarizationMiddleware`：消息较多时压缩早期历史。
- `InMemorySaver`：真正保存 LangGraph 状态。

当前 checkpointer：

```python
checkpointer = InMemorySaver()
```

因此记忆仅存在于当前 Python 进程中，进程重启后消失，没有持久化到 SQLite、Redis 或数据库。

会话隔离：

```python
key_namespace = sha256(api_key.encode()).hexdigest()[:16]
thread_id = f"{key_namespace}:{conversation_id}"
```

这可以避免不同 BYOK Key 的用户因为 `conversation_id` 相同而共享记忆，内存中使用的是 Key 摘要，不是原始 Key。

当前统一检索是无状态的固定 RAG 链路；以下 Agent 记忆仅属于历史实现。

## 五、流式输出

### 1. 模型层

文件：`backend/app/services/chat_service.py`

```python
for message_chunk in chat_model.stream(prompt):
    content = message_chunk.content
    if content:
        yield content
```

模型每生成一小段就通过 `yield` 返回，不需要等待完整答案。

### 2. 内部事件

项目统一使用两类核心事件：

```python
RagStreamEvent(event="sources", sources=[...])
RagStreamEvent(event="token", content="...")
```

### 3. FastAPI SSE

文件：`backend/app/api/chat.py`

```python
def sse_event(event_name: str, data: dict) -> str:
    return f"event: {event_name}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"
```

事件类型：

- `stage`：精排模型准备进度。
- `meta`：查询改写结果和来源。
- `token`：答案片段。
- `done`：回答结束和耗时。

```python
return StreamingResponse(
    event_stream(),
    media_type="text/event-stream",
    headers={"Cache-Control": "no-cache"},
)
```

### 4. 前端渲染

分离版前端逐行读取 SSE：

```python
for line in response.iter_lines():
    ...
```

收到 Token 后：

```python
answer += payload["content"]
answer_placeholder.markdown(f"{answer}▌")
```

当前默认 `streamlit_demo.py` 不经过 HTTP，而是直接消费 Python generator，因此仍有流式效果，但不属于网络 SSE。

## 六、命中图片块后的回答和展示

图片块结构：

```python
Document(
    page_content=description,
    metadata={
        "image_path": local_path,
        "is_image_chunk": True,
        ...
    },
)
```

检索命中后，后端传给大模型的是：

```python
content = result["content"]
image_path = result.get("metadata", {}).get("image_path")

if image_path:
    content = f"[图片资料：{image_path}]\n{content}"
```

大模型总结的是导入阶段产生的图片描述，并不会在检索阶段重新读取原图。

后端同时构造来源对象：

```python
SourceChunk(
    file_name=...,
    header_path=...,
    chunk_id=...,
    content_preview=...,
    image_path=metadata.get("image_path"),
)
```

前端展示：

```python
if source.image_path:
    st.image(source.image_path)
```

所以最终效果是：

- 大模型根据图片描述生成文字答案。
- 前端根据 `image_path` 显示原图。
- 页面同时显示来源文件、标题路径和内容预览。

当前 `image_path` 是服务器本地绝对路径，适合单机 Demo。前后端分离部署时应改成受保护的图片接口或短期签名 URL，避免路径不可访问和服务器目录泄露。

### 聊天图片只辅助检索

聊天时临时上传的图片不会入库，也不会直接作为最终回答依据。系统先压缩图片，再由 Vision 生成描述，并通过 `retrieval_hint` 将描述与用户问题一起用于检索：

```python
prepare_rag_answer(
    original_query=question,
    retrieval_hint=f"图片内容：{description}",
    ...,
)
```

`retrieval_hint` 只参与查询改写和召回；生成阶段仍使用原始用户问题，并且只把最终命中的笔记片段交给回答模型。没有可靠笔记时沿用原有拒答，不根据聊天图片直接生成答案。

## 七、DeepSeek API Key 校验与拦截

### 1. 真实有效性验证

文件：`backend/app/services/multimodal_service.py`

```python
async def validate_deepseek_api_key(api_key: str) -> None:
    url = f"{DEEPSEEK_API_BASE_URL.rstrip('/')}/models"

    response = await client.get(
        url,
        headers={"Authorization": f"Bearer {api_key}"},
    )

    if response.status_code in {401, 403}:
        raise InvalidApiKeyError(...)

    response.raise_for_status()
```

判断规则：

- `2xx`：有效。
- `401/403`：无效。
- 超时或其他网络错误：暂时无法连接 DeepSeek。

验证接口：`POST /api/key/validate`。

### 2. 前端拦截

验证成功后，Streamlit 保存当前 Key 和已验证 Key：

```python
st.session_state.deepseek_api_key = api_key
st.session_state.validated_api_key = api_key
```

只有两者完全相同才认为当前 Key 已验证。用户修改 Key 后必须重新验证。

前端会禁用或阻止：

- 笔记和图片上传
- 删除按钮
- 知识库和看板入口
- 聊天输入

### 3. 后端拦截

文件：`backend/app/core/auth.py`

```python
def require_user_deepseek_api_key(api_key=Header(...)) -> str:
    cleaned_key = (api_key or "").strip()
    if not cleaned_key:
        raise HTTPException(status_code=401)
    return cleaned_key
```

这里目前只检查 Key 是否非空，没有每次联网验证真伪。

因此准确说法是：

- 前端会联网真实验证 Key，再解锁 UI。
- 后端业务依赖主要阻止缺少 Key 的请求。
- 假的非空 Key 可能通过后端依赖，直到真正调用 DeepSeek 时才失败。

当前安全缺口：

- 删除接口只检查 Key 非空，假 Key 也可能执行删除。
- `GET /api/notes` 当前没有 Key 依赖，可以直接读取知识库列表。
- 正式部署前应在后端建立真正的身份认证和授权体系。

## 八、面试时可直接使用的项目介绍

> 项目在 Markdown 导入阶段加入了多模态预处理。后端通过正则提取 Markdown 图片引用，支持 ZIP 内本地图片、HTTPS 图片和 Base64 Data URI。图片会转成 Base64 Data URL 交给 DeepSeek Vision，生成的描述一方面回填到原 Markdown，另一方面生成携带图片路径和标题层级的独立图片块，然后与普通标题块一起写入向量库。
>
> 当前统一检索采用向量检索与 BM25 双路召回，各取 Top-6，再通过 RRF 按排名融合，最后使用 BGE Cross-Encoder 精排得到 Top-3。若命中图片块，大模型根据图片描述组织答案，前端根据来源数据中的图片路径展示原图。
>
> 聊天时上传的图片走请求级辅助检索：图片压缩后由 Vision 生成描述，描述与用户问题一起用于查找相关笔记，但不会进入最终回答上下文；没有可靠笔记时明确拒答。
>
> 项目早期快速模式曾使用 LangGraph Agent、`InMemorySaver` 和 `SummarizationMiddleware`；当前已统一为固定混合检索 Workflow，不再调用这条 Agent 链路。答案仍通过生成器逐块输出，FastAPI 包装为 `stage/meta/token/done` SSE 事件。

## 九、当前项目边界

- Markdown 只按 H1/H2/H3 切分，没有长块二次切分。
- 图片描述会同时存在于增强正文块和独立图片块中，存在一定内容重复。
- 当前统一检索暂不使用多轮记忆。
- `agent_service.py` 只保留早期 Agent 方案，避免把历史实现误说成当前能力。
- 检索命中图片后不会再次调用视觉模型，而是使用导入阶段的描述。
- 聊天图片目前只辅助检索，不支持脱离笔记库直接讲解图片。
- 图片来源当前返回本机绝对路径，不适合前后端跨主机部署。
- 后端 Key 依赖主要检查非空，不是完整认证授权系统。
