# 个人笔记复习助手：面试问答笔记

## 新增：为什么这是 Agentic RAG，而不只是固定 RAG 链路？

> 我把两种模式拆开：快速模式没有用关键词规则决定是否检索，而是给问答模型定义了 `search_personal_notes` 工具。Agent 根据问题自主判断：基础问候和产品使用问题直接回答；需要依据学习笔记的技术问题则发起工具调用，并只做向量检索。精确查找则不经过 Agent，固定走查询改写、向量加 BM25、RRF 和 Cross-Encoder。快速模式的检索结果会作为 ToolMessage 回传给 Agent，最终回答被约束为只依据工具结果生成。这里的边界是单 Agent、单工具，不把它包装成多 Agent 系统。

### 追问：Agentic 会不会更慢？

会。需要查资料的问题多了一次 Agent 决策调用；但基础问答可以直接结束。项目通过 SSE 返回端到端 `elapsed_ms`，在前端展示真实耗时。当前没有编造优化数字，也还没有做答案缓存；后续会先根据耗时数据决定是否缓存高频、无会话依赖的问题。

> 使用规则：以下答案以本项目实际完成情况为准。没有跑出的数据不报数字；没有实现的功能直接说“本期未做，但我会这样考虑”。

## 一、30 秒项目介绍

> 我做的是一个面向学生的个人笔记复习助手。用户导入自己的 Markdown 学习笔记后，可以用自然语言提问，系统会先把口语化问题改写成完整查询，再通过向量检索和 BM25 双路召回，用 RRF 融合、Cross-Encoder 精排，最后只依据命中的笔记片段生成回答并展示来源。它主要解决笔记分散、复习时难以定位原文的问题；知识库没有依据时会明确拒答。前端用 Streamlit，后端用 FastAPI，核心目标是让回答可追溯而不是做泛聊天。

## 二、项目与业务场景

### Q1：为什么做这个项目？

**答：**学生的课程和技术笔记通常散在多个 Markdown 或 PDF 文件里，复习时知道概念但找不到原文，也容易把相近概念混在一起。这个项目把个人笔记变成可检索的知识库，回答时附上文件和章节出处，用户可以直接回看原文。

**边界：**它服务个人学习资料，不是通用搜索引擎，也不保证回答互联网知识。

### Q2：为什么要用 RAG，不直接让模型回答？

**答：**模型参数中没有用户私有、持续更新的学习笔记，而且普通回答无法证明依据来自哪里。RAG 在生成前动态检索笔记片段，把片段和问题一起交给模型，并要求显示来源；因此更适合“基于指定资料复习”的场景。

### Q3：不用 RAG 可以怎么做？为什么没选？

**答：**如果只是固定问答或少量规则提示，用普通 Prompt 或写死 FAQ 更简单。但笔记会不断增加，问题也不可预设，且用户需要回看出处，所以选择 RAG。微调更适合稳定风格或能力迁移，不适合频繁变动的个人笔记。

### Q4：项目最核心的价值是什么？

**答：**不是“能聊天”，而是“回答有依据、能回到原文”。学习时用户可以验证答案，而不是盲信模型。

### Q5：这个项目和普通 RAG Demo 有什么区别？

**答：**普通 Demo 常只有向量检索后直接回答。本项目针对真实笔记问答加入查询改写、BM25 关键词召回、RRF 融合和 Cross-Encoder 精排，并且保留来源和资料不足拒答。每个环节都有明确问题，而不是堆技术名词。

## 三、完整链路与数据处理

### Q6：完整链路是什么？

**答：**离线侧先导入 Markdown 笔记，按标题层级切分，给片段补充文件名、标题路径和片段 ID 等元数据；然后建立向量索引和 BM25 索引。在线侧先改写用户查询，再走向量检索和 BM25 双路召回，用 RRF 融合候选，再由 Cross-Encoder 精排，最后把最相关片段连同来源交给模型生成回答。

### Q7：为什么优先支持 Markdown？

**答：**Markdown 自带标题层级，能用标题感知切分保留“这段文字属于哪一章”的结构；这既提升检索语义，也方便来源回看。PDF 可以后续支持，但解析质量和章节结构更不稳定，所以不是第一优先级。

### Q8：笔记切分时保存哪些元数据？

**答：**至少保存 `chunk_id`、文件名、标题路径、正文和导入时间。`chunk_id` 用于稳定追踪同一片段；文件名和标题路径用于 UI 展示来源；以后如果做更新或删除，也能按来源文件定位。

### Q9：Chunk 为什么不能太小或太大？

**答：**太小会把定义、条件和例子拆散，模型拿不到完整上下文；太大会混入多个主题，召回噪声变大、Token 也更多。我的优先策略是按 Markdown 标题保留语义边界，再结合真实问题观察来源命中和回答质量，而不是套一个所谓行业标准数字。

### Q10：Overlap 有什么作用？

**答：**Overlap 用来保护恰好落在切分边界的信息，例如定义的前半句在上一块、限制条件在下一块。它不是越大越好，过大会带来重复片段、重复召回和额外上下文成本。

### Q11：笔记更新后怎么处理？

**答：**v1 的做法是按文件重新切分并重建该文件对应的索引，避免旧片段残留。数据量很小时，全量重建也更简单可靠；数据规模变大后才考虑增量更新和版本管理。

## 四、查询改写

### Q12：为什么要做查询改写？

**答：**真实提问常带上下文或指代，例如“刚才那个融合有什么优点”。这种句子直接检索时关键词不完整。改写会把它变成“RRF 融合在混合检索中的优点是什么”这类独立问题，帮助向量检索理解语义，也让 BM25 有更明确的关键词。

### Q13：查询改写会不会改错用户意思？

**答：**会有风险，所以它只做补全指代、保留专业术语和去除口语噪声，不负责擅自扩展问题。改写调用失败、输出为空或明显异常时，回退原问题继续检索；回答生成阶段仍使用原始问题，避免用户意图被完全替换。

### Q14：为什么不一开始就做多轮对话记忆？

**答：**多轮记忆会引入历史摘要、上下文截断和隐私管理问题。本期先用查询改写解决最常见的指代问题，保持链路短、可解释；多轮记忆是后续增强，不是 MVP 前提。

## 五、混合检索、RRF 与精排

### Q15：为什么不能只用向量检索？

**答：**向量检索擅长语义相近，但函数名、缩写、公式名和专有术语更依赖精确关键词。个人技术笔记里这类内容很多，所以加入 BM25 补充召回。

### Q16：BM25 是什么，适合解决什么问题？

**答：**BM25 是基于词项匹配的稀疏检索算法，会综合关键词出现频率、文档长度等因素给文档打分。它适合术语、函数名和缩写等精确匹配；但它不理解近义表达，所以要与向量检索配合。

### Q17：中文为什么需要分词？

**答：**BM25 的基本单位是词项，但中文句子没有天然空格。项目用 `pkuseg` 把文本和查询切成词，再建立 BM25 索引；分词质量会影响关键词召回，所以它也是需要关注的环节。

### Q18：为什么要同时做向量检索和 BM25？

**答：**两者互补：向量检索负责语义召回，BM25 负责精确关键词召回。目标不是让其中一个替代另一个，而是让候选池更完整。

### Q19：为什么用 RRF 融合？

**答：**向量相似度和 BM25 分数的尺度不同，直接相加没有可靠含义。RRF 只利用每路结果的排名，将同一文档在多路出现的排名贡献累加，因此对分数尺度不敏感，实现简单且稳定。

### Q20：RRF 的 k 参数有什么作用？

**答：**RRF 的形式是 `1 / (k + rank)`。k 越大，排名之间的分差越平缓；k 较小时更偏向前排结果。它不是固定真理，项目先使用常见起点，再在固定问题集上观察候选排序和回答噪声。

### Q21：为什么 RRF 后还要 Rerank？

**答：**RRF 是较快的候选融合，解决“相关片段有没有进入候选池”。Cross-Encoder 会把“问题和候选片段”成对输入模型细致判断相关性，解决“真正有用的片段能不能排到前面”。

### Q22：Rerank 能解决所有检索问题吗？

**答：**不能。它只能重排已经召回的候选。关键资料根本没进入候选池时，要回到文档解析、切分、查询改写、Embedding 或召回策略排查。

### Q23：Rerank 的代价是什么？

**答：**Cross-Encoder 需要对每一个“查询+候选片段”打分，候选越多延迟越高。因此我只对 RRF 后有限数量的候选精排，而不是对全库文档精排。

### Q24：Top-K 怎么选？

**答：**K 增大可能提高召回覆盖，但也会增加噪声、Token 和延迟。项目不会宣称一个固定最佳值，而是在少量候选范围内用固定问题观察：正确来源是否进入 Top-K、最终回答是否被噪声干扰、响应是否可接受。

## 六、生成、引用与 Agent

### Q25：如何降低模型脱离笔记乱答？

**答：**Prompt 明确要求只依据提供片段回答，并要求附上来源；检索结果不足或相关度不够时返回“当前笔记库资料不足”。这不能保证零幻觉，但能降低无依据回答，并让用户核对原文。

### Q26：来源引用如何实现？

**答：**切分时每个片段带有文件名、标题路径和 `chunk_id`。最终精排结果会连同这些元数据返回给前端，前端在答案下展示来源卡片和原文预览。来源不是模型临时编的，而是检索链路携带的元数据。

### Q27：笔记库没有答案时怎么办？

**答：**不强迫模型回答。根据最终片段数量或相关性判断资料是否不足；不足时提示用户当前笔记库没有足够依据，并建议导入相关资料。这比生成看似合理的答案更符合学习场景。

### Q28：为什么项目里要用 Agent？

**答：**核心问答链路不依赖 Agent，重点仍是检索质量。Agent 是有余力时的扩展：当系统既有“笔记问答工具”又有“章节小测工具”时，让单 Agent 根据用户意图选择工具。这样有明确任务路由价值，而不是为了展示 Agent 让所有问题多走一步。

### Q29：为什么不做多 Agent 或 LangGraph？

**答：**当前只有问答和小测两个明确任务，多 Agent 会增加编排、状态和排障复杂度，但不能直接改善核心检索准确率。实习项目优先把一条主链路做完整、能解释、能演示，再考虑复杂架构。

## 七、排障与简单验证

### Q30：回答不准确时怎么排查？

**答：**先看最终 Top-K 中是否有支撑正确答案的片段。没有，优先排查资料覆盖、切分、查询改写、Embedding、BM25 和召回；有但排序靠后，检查 RRF、候选数量和 Rerank；有且位置合理但回答仍错，检查 Prompt、上下文冲突或模型生成。一次只改一个变量。

### Q31：怎么证明混合检索或精排真的有帮助？

**答：**本项目不做 RAGAS 或生产级评测，但会准备固定的 10 个已知答案问题，对比“只向量检索”和“混合检索+精排”时正确来源是否进入 Top-3，并保留失败案例。只有跑出的记录才会写进 README 或面试回答。

### Q32：为什么不做 RAGAS？

**答：**我在学习阶段已做过基础 RAGAS 实操，但这个项目的目标是完成可运行的个人学习工具，不是搭一套评测平台。v1 用小型固定问题集做回归验证，优先保证链路和用户体验；后续若要比较更多参数或版本，再引入更系统的评测。

### Q33：如果混合检索反而效果变差怎么办？

**答：**不会默认保留它。先检查分词、BM25 候选、RRF 参数和候选数，再看失败题是否本身更适合语义检索。如果固定问题集上没有收益或噪声更大，就保留较简单的方案，并在 README 说明该边界。

### Q34：项目有哪些局限？

**答：**它是本地单用户 Demo，没有真实线上流量、高并发、权限体系和大规模评测；资料质量直接影响回答质量；Rerank 会增加延迟；当前主要优化 Markdown 笔记，复杂 PDF 解析还未重点处理。

## 八、工程、前端与安全

### Q35：为什么用 FastAPI 和 Streamlit？

**答：**FastAPI 负责把导入、问答、小测能力封装成清晰接口，便于后续替换前端或测试；Streamlit 适合快速完成学习工具界面和演示。这个组合开发成本低，适合单用户本地 MVP。

### Q36：前后端接口会返回什么？

**答：**问答接口至少返回：原问题、改写后问题、回答文本、是否资料不足、来源列表。每条来源包含文件名、标题路径、原文预览和片段 ID。这样 UI 只负责展示，不需要理解检索实现。

### Q37：为什么展示改写后的查询？

**答：**它默认折叠展示，帮助用户理解系统到底检索了什么，也方便排查改写是否偏题；但不会用一大段底层日志干扰正常复习体验。

### Q38：如何保护 API Key 和个人笔记？

**答：**密钥只从 `.env` 读取，`.env` 加入 `.gitignore`，不写进代码、README、页面或日志。v1 是本地单用户工具，笔记默认只在本地处理；若未来做云端，才需要补账号、权限、加密和数据删除机制。

### Q39：前端是谁做的？你负责什么？

**答：**前端 UI、交互和前后端联调由 Codex 协助完成；我负责提出学习场景与验收标准，并重点理解和验证 RAG 主链路、数据输入输出、检索策略与结果。面试时我只讲自己能运行、修改和解释的部分，不把协作成果全部说成独立完成。

## 九、面试必须避免的说法

- 不说“Rerank 一定提升准确率”；要说它解决候选排序问题，最终以实际验证为准。
- 不说“Chunk=500、Overlap=100 是行业标准”；要说根据文档结构、问题粒度和验证结果选择。
- 不说“RAG 能彻底消除幻觉”；要说它提供外部依据、引用和拒答机制，降低无依据回答。
- 不说“项目已经生产部署”；它是本地单用户 Demo。
- 不把课程里的 RAGAS 结果冒充为本项目的真实指标。
- 不把 Codex 协助完成的 UI 或代码说成自己独立从零实现。

## 十、3 分钟讲解顺序

1. **场景（20 秒）**：个人笔记分散，复习难找原文，因此做带引用的笔记助手。
2. **离线侧（35 秒）**：Markdown 标题切分、元数据、向量与 BM25 索引。
3. **在线侧（60 秒）**：查询改写、双路召回、RRF、精排、只依据资料回答。
4. **一个取舍（35 秒）**：解释“混合检索补召回，精排提排序”，以及精排延迟代价。
5. **验证与边界（30 秒）**：固定 10 题对比来源 Top-3；本地单用户 Demo，不宣称生产指标。
# Q40：为什么项目中要提供快速模式和精确查找？

**答：** 两种模式对应不同约束。快速模式只使用向量检索，适合概念解释和日常复习，少了查询改写、BM25 和精排的额外耗时；精确查找使用查询改写、向量检索、BM25、RRF 与 Cross-Encoder，适合缩写、函数名和需要更可靠来源的术语问题。这样不是堆技术，而是把检索质量、延迟和成本的取舍显式交给用户。两条链路都只依据笔记回答，资料不足时都要拒答。
